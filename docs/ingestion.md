# 記事の投入口をどう作るか — 提案

`articles/` に記事が入りさえすれば分析は自動で走る（実装済み）。
残る問題は「誰が・何を使って・どうやって記事を入れるか」だけ。ここを Claude に依存させない設計にする。

版: v1 / 2026-08-15

---

## 結論

**投函口を3つ作る。全部 GitHub Actions で完結させ、外部サービスへの依存とアカウント管理を増やさない。**

| # | 投函口 | 使うもの | 何が入るか | 手間 |
|---|---|---|---|---|
| **A** | 自動収集 | GitHub Actions（毎朝）+ RSS | 定常的に見張る情報源 | 初期構築だけ |
| **B** | 手で拾う | GitHub Issue | たまたま見つけた重要記事 | URL を貼るだけ |
| **C** | まとめ投入 | CSV を置く | 過去分の一括投入、他ツールからの書き出し | すでに動く |

A が主軸、B が保険、C は移行用。**Claude は一切要らない**（構築が終われば）。

そして A の中身で効くのが次の一点です。

> **Google アラートの RSS 配信を情報源にする。**
> キーワードを登録すると、それに合致するニュースの RSS フィード URL がもらえる。
> 認証不要、スクレイピング不要、URL を `sources/` に1行足すだけで監視対象が増える。

「世界各国から自動的に集める」という当初の目的に対して、これが最も費用対効果が高い入口です。

---

## A. 自動収集（主軸）

### 仕組み

```
毎朝 06:00 JST  GitHub Actions (cron)
      ↓
sources/*.yaml を読む
      ↓
 ┌── 公式RSS ────────── 文部科学省, 都道府県, 独法 …
 ├── Google アラートRSS ─ 「文化政策」「文化庁」「文化財 保存」「cultural policy」…
 └── HTMLスクレイプ ──── 文化庁（RSSが無い）, 文化審議会
      ↓
URL 正規化 → 既出なら捨てる（doc_id で冪等）
      ↓
articles/2026/08/<source>-<hash>.md を書く
      ↓
git commit → push
      ↓
（既存の analyze ワークフローが発火して out/ が更新される）
```

収集と分析を**別のワークフローに分ける**のが要点です。収集が1ソース失敗しても分析は走り、
分析のバグで収集が止まることもありません。

### 情報源の3系統

**① 公式 RSS** — 一次情報。文部科学省には RSS があります。自治体・独法も多くが配信しています。
最も信頼できるので `tier: primary` として本文まで保存します。

**② Google アラートの RSS 配信** — キーワード監視。ここが自動収集の主力です。

- [google.com/alerts](https://www.google.com/alerts) でキーワードを登録し、配信先を **「RSS フィード」** に変更する
- **注意: 「ダイジェスト」がオンだと RSS を選べません。** 歯車アイコンからダイジェストのチェックを外してから設定します
- RSS ボタンを右クリック → リンクをコピー → `sources/*.yaml` に貼る
- 更新は 1日3〜4回程度。頻度の指定はできません

登録するキーワードの案（日本の文化政策・フェーズ1）:

| キーワード | 狙い |
|---|---|
| `文化庁` | 実施主体の動き全般 |
| `文化政策` | 言説そのもの |
| `文化財 保存` / `文化財 活用` | 保存と活用の綱引き |
| `文化観光` | 観光振興との接続 |
| `博物館 学芸員` | 人材・制度の問題 |
| `劇場 助成 OR 補助金` | 支援の配分 |
| `文化芸術基本法 OR 博物館法 OR 劇場法` | 法制度の動き |

国際比較（フェーズ3）に進むときは、言語と地域を指定した `cultural policy`、`Kulturpolitik`、
`politique culturelle` などを足せば、同じ仕組みのまま多言語に伸ばせます。

**③ HTML スクレイプ** — RSS が無いところ用。文化庁の「広報・報道・お知らせ」はこれ。
一覧ページを取得して前回との差分を取ります。パーサは `kind: html_list` の1本だけを使い回し、
サイトごとの違いは YAML のセレクタで吸収します（サイト改修で壊れるので `fixtures/` に
固定HTMLを置いて回帰テストを付ける）。

### ソース定義

コードを増やさずソースを増やせる形にします。

```yaml
# sources/google_alert_bunkazai.yaml
id: ga_bunkazai
name: Googleアラート「文化財 保存」
kind: rss
url: https://www.google.com/alerts/feeds/00000000000000000000/0000000000000000000
country: JP
lang: ja
tier: secondary        # 報道 → 見出しとRSS要約のみ保存（本文は取りに行かない）
enabled: true
```

```yaml
# sources/bunka_hodo.yaml
id: bunka_hodo
name: 文化庁 広報・報道・お知らせ
kind: html_list
url: https://www.bunka.go.jp/koho_hodo_oshirase/
list_selector: "main ul li a"
date_selector: "main ul li time"
body_selector: "main"
tier: primary          # 官公庁の公表資料 → 本文を保存してよい
rate_limit_sec: 3
```

### 保存するものを tier で分ける（著作権）

ここは仕組みで守ります。人間の注意力に頼ると必ず破られます。

| tier | 対象 | 保存するもの |
|---|---|---|
| `primary` | 官公庁・独法の公表資料 | **本文まで** |
| `secondary` | 報道記事 | **見出し + RSS の要約 + URL のみ**。本文は取得しない |

**分析上もこれで困りません。** 見出しは本文より情報密度が高く、共起の質に効くのはむしろ見出し側です。
全文を追いかけて本文抽出ライブラリと格闘するより、見出し+要約で母数を増やす方が図はよくなります。

### GitHub Actions の運用上の注意（実際に踏むもの）

- **cron は UTC。** 06:00 JST は `0 21 * * *`。
- **時刻は正確ではありません。** 5〜30分の遅延は日常茶飯事で、混雑時は1時間ずれることもあります。
  「毎朝だいたい」で困らない設計にしておくこと。
- **60日間リポジトリに動きがないと、スケジュールが自動で無効化されます。**
  ただし本件は収集ジョブ自身が毎日コミットするので、これは自動的に回避されます。
  逆に言えば「記事が1件も増えない日が60日続く」と止まるので、その場合は気付ける必要があります。
- **無料枠。** private リポジトリの Actions 実行時間には月あたりの上限があります（プランによる）。
  1日1回・3分程度なら月100分弱で、まず問題になりません。
- **収集ジョブは `[skip ci]` を付けない**（付けると analyze が発火しません）。
  逆に analyze の書き戻しコミットには付ける（すでにそうしてあります）。

## B. 手で拾う → GitHub Issue を投函口にする

自動収集は必ず取りこぼします。「これは入れておきたい」と思った記事を、
**スマホの GitHub アプリから URL を貼るだけ**で投入できるようにします。

```
Issue を立てる（テンプレートに URL を貼る）
      ↓
Actions が発火 → URL を取得 → 見出しと日付を抽出 → articles/ に .md を作成
      ↓
Issue に「取り込みました」とコメントして自動クローズ
```

- 専用アプリもアカウントも要りません。GitHub アプリの共有シートから飛べます
- 取り込みに失敗したら Issue が開いたまま残るので、取りこぼしが可視化されます
- `tier` は Issue のラベルで指定（`primary` / `secondary`）

これが「Claude と別に入れる」の最も素直な答えです。IFTTT も Zapier も要りません。

## C. まとめ投入 → CSV（すでに動く）

過去分の一括投入や、他ツール（Zotero、スプレッドシート、RSS リーダーの書き出し）からの
移行はこれで足ります。`title,body,date,source,url` の CSV を `articles/` に置くだけです。

## 検討したが採らなかったもの

| 選択肢 | 却下理由 |
|---|---|
| **IFTTT / Zapier / Make**（RSS → GitHub） | 動くが、無料枠が薄く、監視対象が増えるほど課金が効いてくる。何より**設定が GUI の中に隠れてリポジトリから見えない**。sources/*.yaml で管理できる利点を捨てることになる |
| **Gmail 転送 + IMAP 取り込み** | Google アラートをメールで受けて Actions が読む形。動くが、認証情報を Secrets に持つ手間が増える。**RSS 配信を使えば認証そのものが不要**なので、わざわざメールを経由する理由がない |
| **Google スプレッドシートを投函口に** | 非技術者と共同で記事を集めるなら有力。サービスアカウントの発行が要る。今は1人運用なので過剰 |
| **Inoreader / Feedly の Webhook** | RSS を束ねる用途では優秀だが有料プラン。Google アラート + 公式RSS で足りる |
| **ブラウザ拡張・ブックマークレット** | PC からの手動投入には快適だが、B（Issue）でスマホも PC も両方カバーできる |
| **RSSHub** | RSS の無いサイトを RSS 化する。公開インスタンスは不安定、自前ホストは運用対象が増える。文化庁1サイトのために背負うものが大きい |

## 実装の順序と工数

| Step | 内容 | 目安 |
|---|---|---|
| **1** | `pipeline/collect.py` + `sources/*.yaml` + 収集ワークフロー。まず公式RSS 1本で end-to-end | 半日 |
| **2** | Google アラートを5〜7本登録し、`sources/` に追加 | 30分（手作業） |
| **3** | Issue → 記事の投函口 | 1時間 |
| **4** | 文化庁の HTML スクレイパ + `fixtures/` 回帰テスト | 半日 |
| **5** | GDELT で多言語に広げる（フェーズ3） | 1日 |

Step 1 と 2 が終われば、**翌朝から記事が勝手に増えて図が更新される**状態になります。

---

## 先に決めておくべきこと

1. **リポジトリを public にするか。** public にすると Gephi Lite に URL を渡すだけで開けるようになりますが、
   `articles/` の中身も公開されます。報道記事は見出し+要約に留める運用（tier 分離）が前提条件になります。
2. **収集の頻度。** 毎朝1回で十分だと考えています。文化政策のニュースは1日に何十本も出るものではなく、
   時系列の surprise 指標も日次で意味を持つ粒度です。
3. **取りこぼしの許容度。** Google アラートは網羅的ではありません（Google のインデックス次第）。
   「全部拾う」を目指すとスクレイパの数だけ壊れる箇所が増えます。B の Issue 投函口があるので、
   自動収集は**8割拾えれば良い**と割り切るのが運用が続くコツです。
